# Chapter 9: Batch

## Core Idea
小批量能更快暴露缺陷、更快获得客户反馈，从而缩短 Build-Measure-Learn 循环。批次越大，返工与等待越隐蔽，最终可能陷入“大批次死亡螺旋”。

## Frameworks Introduced
- **Single-piece flow / small batches**：每次只推进一个最小可交付单位；目标是更快学习与更早发现错误，而非单台机器利用率。
  - How：① 识别工作流转的所有阶段；② 把“一次交付的单位”压到最小；③ 为每个阶段配即时的缺陷检测与反馈；④ 用 pull（待验证假设）而非部门推动来排优先级。
  - 信封类比：逐个装完一封，比“先折 100 封信再贴 100 张邮票”更快，因为省去了在堆积半成品间分拣、搬运与返工的时间。
- **Pull, don't push**：后道工序按实际需求拉动前道工序；在 startups 中，拉动信号是“需要验证的假设”，不是客户直接下订单。客户常说不知道自己要什么，所以不是客户在拉动，而是我们对客户的假设在拉动。
- **Continuous deployment**：每次小改动都立即发布给部分客户，配合自动检测和“免疫系统”快速回滚。

## Key Concepts
- **Batch size**：从一个阶段流向下一个阶段的工作量。
- **WIP（work-in-progress）**：尚未交付/验证的半成品工作，包括设计、假设和计划。
- **Andon cord**：任何员工发现问题即可拉停流程；在软件中对应自动监控与自动回滚。
- **SMED（Single-Minute Exchange of Die）**：把机器换型时间从小时级压到分钟级，是小批量制造的基础。
- **Large-batch death spiral**：返工与延迟导致批次越做越大，最终难以发布；“反正已经做这么久了，不如再修一个 bug/再加一个功能”。

## Mental Models
- 问“如果客户不想要，多久能知道？”批量越小，答案越早。
- 局部效率不等于系统效率；单点满负荷可能拖慢整个循环。
- 先缩短从假设到证据的路径，再考虑扩大生产。
- 硬件/快速原型/软件化三条趋势让小批量在非软件行业也成为可能（3D 打印、快换产线、软件化硬件）。

## Anti-patterns
- 按部门大批量交接（设计→工程→测试→发布）。
- 认为批量越大、单位成本越低，就必然越高效。
- 用“发布前再多修一个 bug/再加一个功能”推迟验证。
- 用一次性大型发布替代持续小步反馈。
- 只做自动化功能测试，忽略业务后果（例如按钮变成白底白字，功能测试全过但客户无法购买）。

## Worked Example
IMVU 让设计与工程围绕单个功能并肩工作，功能就绪即向小比例用户发布并观察行为；每天平均上线约 50 次。自动测试与业务监控构成“免疫系统”，发现缺陷即自动移除变更、通知团队并阻止后续变更，直到根因修复。Wealthfront 在受 SEC 监管环境下也做到每日十余次发布。

## Key Takeaways
1. 缩小批次以更早发现质量与需求错误。
2. 用 pull 机制让验证需求拉动开发，而非部门推动。
3. 建立自动检测、回滚与根因分析，保护发布速度。
4. 在硬件/服务等非软件领域，同样寻找可缩短反馈路径的“小批量”设计。
