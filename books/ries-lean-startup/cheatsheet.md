# Cheatsheet

## 决策规则
- **若无法说出会推翻假设的结果** → 这不是实验；先写失败条件。
- **若一项工作不能改变客户行为或降低关键不确定性** → 视为 waste。
- **若指标总量上升但 cohort 未改善** → 不要庆祝；你在看 vanity metrics。
- **若多轮调优后增长驱动因素仍不动** → 进入 pivot 讨论，而非继续优化。
- **若客户不使用/不付费** → 先怀疑价值假设或客户群，不要先怪执行质量。
- **若增长停滞** → 先识别引擎：sticky 看 churn，viral 看 K，paid 看 LTV−CPA。
- **若同一错误第二次出现** → 必须做根因预防投资（Five Whys）。
- **若创新团队被要求“先证明能成功再给资源”** → 用沙盒的小实验与学习里程碑换取自主权。

## Pivot-or-Persevere 决策树
1. 核心指标是否在**方向**上改善（不只绝对值）？
   - 是 → 继续调优；设下一次评审点。
   - 否 → 2。
2. 是执行问题，还是战略假设问题？
   - 执行可修复 → 小批量修复并复测。
   - 关键假设被证伪 → 3。
3. 保留什么？
   - 客户关系/技术/渠道中哪部分仍有效？
4. 选择 pivot 类型（见下表）→ 写新战略假设 → 设计新 MVP。
5. 若没有可行新假设且 runway 将尽 → 缩减或关闭，而非无限 persevere。

## Pivot 类型速查
| 类型 | 改变什么 | 典型信号 |
|---|---|---|
| Zoom-in | 一个功能变成整个产品 | 客户只为某一功能付费 |
| Zoom-out | 产品变成更大产品的一个功能 | 单点功能不足以独立成立 |
| Customer segment | 目标客户群 | 产品有人爱，但不是原定人群 |
| Customer need | 解决的问题 | 客户有更痛的相关问题 |
| Platform | 应用 ↔ 平台 | 第三方生态或自助需求出现 |
| Business architecture | 高毛利低量 ↔ 低毛利高量 | 销售周期/单位经济不匹配 |
| Value capture | 变现方式 | 有人用但无人付费 |
| Engine of growth | sticky/viral/paid | 现引擎接近耗尽 |
| Channel | 销售/分销渠道 | 原渠道成本或覆盖失效 |
| Technology | 实现技术 | 同问题可用更优技术解决 |

## 增长引擎阈值与指标
| 引擎 | 核心指标 | 经验判断 |
|---|---|---|
| Sticky | churn、compounding rate | 新客率 > churn 才增长；compounding≈0 即停滞 |
| Viral | viral coefficient（K） | K<1 会衰减；K 接近 0.9–1.0 才算接近 fit |
| Paid | LTV、CPA/CAC、marginal profit | LTV>CPA 才可持续；差额决定增速 |

## MVP 选择
| 情境 | 首选 | 代价 |
|---|---|---|
| 需求/定位不明 | smoke test、视频 | 只证兴趣，不证留存 |
| 交付流程复杂 | concierge | 不可规模化 |
| 技术可行性未知 | wizard of oz | 人工成本高 |
| 单一功能可验证价值 | 单功能原型 | 可能漏掉系统性体验 |

## 红旗与气味
- 董事会/汇报里只有“up and to the right”的总量图。
- 团队说“我们学到了很多”，但拿不出行为改变或指标改善。
- 每次发布都是大版本，发布前还在加功能。
- 指标口径每月变化，无法做因果推断。
- root cause 分析变成“谁做错了”。
- 创新项目被要求按成熟业务的 ROI 论证，却被藏在黑箱里。
- 客户说喜欢，但留存/付费不动。

## 会议与节奏
- **Pivot-or-persevere**：几周一次太频繁，几个月一次太稀疏；产品与业务共同参加。
- **Five Whys**：新问题出现即开；全员相关方到场；从窄问题开始。
- **沙盒实验**：预设时间上限与客户影响上限；统一 5–10 个指标。
- **学习里程碑**：baseline → engine tuning → pivot/persevere。

## 一句话
> 若不能失败，就不能学习；若不能学习，就只是在高效地浪费。
