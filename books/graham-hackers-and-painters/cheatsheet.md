# Cheatsheet

## 决策规则

| 情境 | 决策 | 理由 |
|---|---|---|
| 要不要创业 | 想要"测量 + 杠杆"就去；只想稳定收入就别去 | 创业压缩痛苦，且全有或全无 |
| 在大公司还是小团队 | 能力强且在意钱 → 小团队；否则大公司也合理 | 小团队让你不被平均值拖累 |
| 选什么技术问题 | 选更难的那个（run upstairs） | 难度是护城河，大公司追不上 |
| 选什么语言 | 控制服务器/整个系统时，用最强语言 | 对手被中位语言粘住，速度差会复利 |
| 要不要公开技术优势 | 创业期尽量不说 | "对手不理解的技术优势最有价值" |
| 软件怎么发布 | 小步、持续、随时可上线 | 大爆炸发布制造复合 bug 与宿命论 |
| 该做用户要的还是你认为对的 | 诊断需求（need），不是照单全收（want） | 用户不知道所有选项 |
| 设计评审通过标准 | 先问"给谁用、解决什么问题" | 脱离用户无法谈好坏 |
| 发现有"设计模式" | 警惕：可能是抽象不足、手工展开宏 | 模式常是人体编译器痕迹 |
| 看到"行业最佳实践" | 对创业公司 = 平均值 = 死亡 | 用它是为了免责，不是最优 |
| 听到 x-ist / y-ic 标签 | 问"它事实上是假的吗" | 标签常替代论证 |
| 有异端想法 | 可以想，谨慎说；找可信小圈子讨论 | 目标是能想，不是能说 |

## 语言选择判断

| 信号 | 含义 |
|---|---|
| 招聘要 Oracle | 最安全、最不危险的对手 |
| 招聘要 C++/Java | 仍安全，技术由"标准"驱动 |
| 招聘要 Perl/Python | 开始危险：技术侧可能有真黑客 |
| 语言是某流行系统的脚本语言 | 有流行潜力（C/Unix、JS/浏览器） |
| 语言没有免费实现/薄书/可 hack 的系统 | 很难形成临界质量 |
| 语言核心公理多而杂 | 长期演化会死掉 |

## 阈值与默认值

- 语言临界质量：**约 20 个独立用户**。
- 团队规模：**<10 人**；成败更取决于**前 5 人**。
- Viaweb：**3 个程序员**；每天 **3–5 次发布**；上线成本 **<$10k**。
- 创业回报分布：均值约 **30×**，中位数**接近 0**。
- Lisp vs C 代码量：**7–10×**；ITA 称 **1 行 Lisp ≈ 20 行 C**。
- Viaweb 宏占比：**20–25%**。
- 贝叶斯过滤器：每 **1,000 封 spam 漏 <5**，**0 false positive**；阈值 **.9**；未见过词 **.4**；取 **15** 个最 interesting token。
- 好设计：**"非常苛刻的品味 + 满足它的能力"**。

## 快速判断（Tells）

- 学校/组织里"地位取决于提升地位" → 宫廷式人气竞赛，不是能力场。
- 一个时代的人对某观点只贴标签不辩论 → 那里可能有真异端。
- 大公司说"我们设计、你们实现" → 设计战可打，但要选新市场。
- 桌面软件一年一两次大发布 → bug 会批量出现，修不完。
- 你的工作"感觉很安全" → 大概率没有杠杆，不会致富。
- 用户第一次用就困惑 → 产品问题，不是文档问题。
- 你的程序里到处是模式 → 语言抽象不够强。
- 你在用"行业最佳实践"安慰自己 → 你选择了平均值。
- 一个语言"很奇怪、大概和我的差不多" → 你可能在 Blub  Paradox 里。
- 设计者自己不用自己的产品 → 设计很可能在腐化。

## 一句话公式

- 创业：**测量（小团队）+ 杠杆（技术）+ 最难的问题 + 最强语言 + 用户数当指标**。
- 好设计：**解决正确问题的简单、timeless、可细化、略带幽默的方案**。
- 语言：**小核心、可 hack、简洁、有库、有 profiler、给时间**。
- 思考：**Always be questioning. What can't you say? And why?**
