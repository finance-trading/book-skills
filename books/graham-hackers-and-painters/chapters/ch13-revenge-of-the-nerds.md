# 第13章：Revenge of the Nerds（书呆子的复仇）

## Core Idea
编程语言**确实有强弱之分**；Lisp 之所以"古老"却不旧，是因为它本质上是**数学而非 1950 年的技术**——1958 年提出的 idea，主流语言直到今天才追上其中一部分。对创业公司而言，"行业最佳实践"得到的只是**平均值**；正确的配方是：找最难的问题，用最强的语言，然后等竞争对手的 pointy-haired boss 回归均值。

## Frameworks Introduced
- **Pointy-haired boss 模型**：这个漫画人物结合了"对技术一无所知"和"对技术有强烈意见"两个通常分开的特质。他选语言的逻辑是："Java 是标准，因为我总在新闻里看到；用标准我就不会犯错，而且永远有 Java 程序员可雇。" 这个逻辑的前提是"所有语言等价"——而这一前提为假。
- **证明语言不等价的绕路**：若 1992 年问 pointy-haired boss 用什么语言，他会立刻答 C++；若语言等价，为什么他的答案会随时间变？为什么 Java 的设计者（Gosling）要发明一门"修正 C++ 问题"的新语言？顺着这条线，"语言等价"的假设就自相矛盾了。
- **Lisp 是数学，不是技术**：Lisp 源于 McCarthy 1958 年的理论练习——比图灵机更简洁的 universal Lisp 函数（eval）。Steve Russell 把它翻译成机器语言，意外得到解释器。所以该与 Lisp 比较的不是 1950 年硬件，而是 1960 年发明、至今仍是最快通用排序的 quicksort。
- **九大 idea（按主流吸收顺序）**：
  1. 条件（if-then-else）
  2. 函数类型（函数是数据）
  3. 递归
  4. 动态类型
  5. 垃圾回收
  6. 由表达式组成的程序（表达式的树，每个表达式有值）
  7. symbol 类型
  8. 用 symbol 与常量的树作为代码记号
  9. "整个语言始终在场"（读/编译/运行互不区分）
  前五项早已普及；第六项开始进入主流；第八、九项是 Lisp 最独特的来源——"用语言自身的数据结构表达语言"，使**写程序的程序（macros）**成为日常。
- **代码长度作为权力度量（Code size as power metric）**：语言越强，同样程序越短；写程序时间主要取决于长度；Lisp vs C 常听到 7–10 倍，ITA 称"一行 Lisp 可替代 20 行 C"。倍数在难题和聪明程序员手中还会更大。
- **Bottom-up programming**：不直接在基础语言里写应用，而是在基础语言上**再建一层"写这类程序的语言"**，然后用这层写程序；结果代码短得多，且修改时语言层常常不用动。
- **Greenspun's Tenth Rule**：任何足够复杂的 C 或 Fortran 程序，都包含一个"ad hoc、非正式规格、带 bug 且缓慢的 Common Lisp 的一半的实现"。
- **配方（The recipe）**：想赢软件生意，就"找你能找到的最难的问题，用你能拿到的最强语言，然后等竞争对手的 pointy-haired boss 回归均值"。

## Key Concepts
- **Lisp vs Fortran as two evolutionary trunks**：Lisp 根植于数学，Fortran 根植于机器架构；两棵树一直在收敛。Lisp 从强变快，主流从快变强，现在最先进的语言已接近 Lisp，但仍缺几样。
- **Macros（Lisp 意义）**：Lisp macro 可从小缩写到"新语言的编译器"；是"写程序的程序"。
- **Centripetal forces**：用冷门语言的三个风险——与其他语言互操作、库更少、招聘困难——大多是**向心力**而非真正障碍：控制整个系统时互操作可自己修；库重要性取决于问题难度；团队<10 人时任何语言都招得到人。
- **ITA / Orbitz 案例**：ITA 的机票搜索引擎是 20 万行 Common Lisp，搜索可能性比 Travelocity/Expedia 多若干数量级；对手仍用大型机时代技术。
- **Industry best practice = average**：Erann Gat 指出，"行业最佳实践"给你的不是最佳，只是平均；在决定让你以竞争对手几分之一速度开发技术的问题上，这名字不合适。
- **Red herring of hiring**：选择更强语言常减少所需团队规模（需要更少人，且用先进语言的人往往更聪明）。

## Mental Models
- 把 pointy-haired boss 想成**风险最小化的中位数**：他选"行业最佳实践"是为了免责，不是为了最优；你应反着来。
- 把 Lisp 想成**quick sort**：老算法不是过时，而是因为它是数学；比较对象错了，结论就错。
- 把语言选择想成**杠杆乘数**：不是"语言稍好一点"，而是"对手花一年，你花三周"，且你的时间可能根本不够。
- 把"patterns"想成**人体编译器的证据**：若你常在程序里看到设计模式，可能说明你的抽象不够强，你在手工生成宏展开。
- 把招聘要求想成**危险信号**：要 Oracle 的是"最安全的对手"；要 Perl/Python 的才像黑客掌舵。

## Anti-patterns
- **"所有语言等价"的舒适假设**：它让你回避同时解两个未知方程（语言适配度 × 生态可得性）。
- **用专利当主要壁垒**：对手常能绕开，或直接侵权并拖你进昂贵漫长的官司；"最好的防御是好的进攻"——做难以复制的技术。
- **让 pointy-haired boss 做技术决策**：你不能用 Lisp，不是因为 VC 害怕，而是因为不用 Lisp 就写不出让他们想买的产品；"因果倒置"。
- **为取悦 VC / 收购方设计产品**：应该取悦用户；如果没赢用户，没人关心你的技术选择多正统。
- **把"设计模式"当优点炫耀**：对作者而言，程序里出现模式往往是抽象不足、手工做编译器工作的危险信号。
- **认为"用弱语言但招更多人"能追上**：Brooks 定律——超过一定规模，新雇的人反而是净损失。

## Worked Example
**累加器（accumulator）代码对比**：求一个函数 `foo(n)`，返回一个函数，该函数接受 `i` 并返回"n 累加 i"（注意是累加，不是加）。

- **Common Lisp**（最短、直接）：
  ```lisp
  (defun foo (n)
    (lambda (i) (incf n i)))
  ```
- **Ruby** 几乎相同：
  ```ruby
  def foo (n)
    lambda {|i| n += i } end
  ```
- **Perl 5**：要手动从 `@_` 取参，因此更长：
  ```perl
  sub foo {
    my ($n) = @_;
    sub {$n += shift}
  }
  ```
- **Smalltalk / JavaScript**：略长；JavaScript 因保留"语句/表达式"区分，需要显式 return。
- **Python**（当时限制较多）：不能完全用 lexical variable，必须用数据结构保存 `n`，且 lambda 无字面表示，要造命名函数：
  ```python
  def foo (n):
    s = [n]
    def bar (i):
        s[0] += i
        return s[0]
  return bar
  ```
- **Java**（最接近的写法用接口+匿名类，但仍"只支持整数"）：
  ```java
  public interface Inttoint {
    public int call (int i);
  }
  public static Inttoint foo (final int n) {
    return new Inttoint () {
      int s = n;
      public int call (int i) {
        s = s + i;
        return s;
      }};
  }
  ```

同一功能，语言越强，代码元素越少；弱语言往往要靠"手工模拟编译器会做的代码分析"（如用类+字段模拟 closure）。这正是 Blub 悖论的量化证据。

## Key Takeaways
1. 语言强弱是真实的；Lisp 的优势不是信仰，而是"代码即数据 + macros"这一可解释的机制。
2. 用代码长度衡量语言权力：短 = 强；强 = 快；快 = 在竞争中的生死线。
3. "行业最佳实践" = 平均值；创业公司应**故意偏离**。
4. 最强语言的价值在**最难问题**上最大；胶水小脚本可以随便用熟悉的语言。
5. 招聘/互操作/库的担忧多是向心力；真正的问题是你的团队规模是否 <10、你是否控制整个系统。
6. 配方：最难的问题 + 最强的语言 + 等对手回归均值。
7. 若你发现自己在写"模式"，检查是否在用弱抽象手工做宏展开。
