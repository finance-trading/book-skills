# 第14章：The Dream Language（梦想语言）

## Core Idea
一种编程语言好不好，**当且仅当黑客喜欢它**——语言是工具，要为人的能力与弱点设计，如鞋为脚设计。一种语言要流行，必须同时提供：一个免费实现、一本薄而好的书、一个值得 hack 的系统（通常是作为某流行系统的脚本语言）。黑客想要的最关键品质，按重要性排列：**hackability（能做你想做的）> 简洁 > 丢弃型程序支持 > 库 > 效率（尤其 profiler）> 时间（被验证的稳定性）**。

## Frameworks Introduced
- **流行性的机制（Mechanics of popularity）**：外部因素（遗产、炒作）有影响，但长期最强的是**专家黑客**——人数极少，却写了所有好软件，并决定他人用什么语言。"给定初始临界质量和足够时间，语言大概会流行到它配得上的程度"；流行反馈又反过来让好语言变好。
- **临界质量 ≈ 20 个独立用户**："如果一个语言有 20 个自己决定使用它的人，我就认为它是真的。" 从零到 20 可能比从 20 到 1000 更难；最好用**特洛伊木马**：给一个人们想要的应用，它恰好写在新语言里。
- **脚本语言规则（Scripting-language-of rule）**：编程语言要流行，必须是某流行系统的脚本语言。Fortran/Cobol 是大型机，C 是 Unix，Perl/Python 是 Unix，Tcl 是 Tk，Visual Basic 是 Windows，Lisp 是 Emacs，PHP 是 web 服务器，Java/JavaScript 是浏览器。"要 hack"是及物动词；语言是相对于它被用来 hack 的东西被评判的。因此要设计流行语言，要么提供比语言更多的东西，要么替换某系统的脚本语言。
- **语言必需的三件套**：免费实现（个人黑客不为软件付钱，但公司会）；薄而好的书（Kernighan & Ritchie 的《C Programming Language》是范本；"出 O'Reilly 的书"成为 hacker 意义上的检验）；在线文档 + 实体书。
- **Succinctness（简洁）**：黑客是懒的，像数学家与现代建筑师；选语言时常以"要敲多少字符"为潜标准。简洁来自更高的抽象；设计者应不断问"这能否用更少 token 表达？"；若一个改动让很多程序变短，多半发现了有用的新抽象。
  - 反例：Cobol 式 `add x to y giving z`；Java hello-world 的样板几乎足以定罪。
  - 个体 token 也应短：Perl 的加密密度 vs Common Lisp 的长内建名；长名字的成本是敲、读、屏幕空间。
- **Hackability（可破坏性/自由度）**：比简洁更重要。语言设计史上惊人多的努力花在**阻止**程序员做"不合适"的事；但设计者无法预知天才程序员需要什么。应假设用户是"一个需要做你想不到的事的天才"，而不是需要被保护的小白——"小白反正会把自己脚射了"。让程序员接触尽可能多的内部实现；"让工具被二次猜想"。好语言应**既干净又肮脏**：内核小且正交，但允许黑客胡来（C、早期 Lisp）。
- **丢弃型程序（Throwaway programs）**：为黑客有吸引力，语言必须擅长写"一小时的小程序"；而最好的大型程序往往起源于此——像二战临时建筑，常常不拆。Perl 本身就是丢弃型程序长成的语言。
  - 要擅长丢弃型：即时可用（已安装）、交互式、启动快、简洁、有库。
- **Libraries（库）**：最简洁的形式是"程序已写好，你只需调用"；未来语言进步主要在库。库要用小集合正交算子设计，让程序员能预测哪个调用做什么；库太大会变成"找函数比写更慢"。
- **Efficiency（效率）**：好语言应生成快代码，但实际速度主要靠 **profiler**，而非静态类型。Knuth：速度只在关键瓶颈处重要；人们常猜错瓶颈。好的 profiler（甚至"主动 profiler"把性能数据推给程序员、把瓶颈标红、用声音提示）比"生成快代码的编译器"更重要。
  - 服务器应用的关键效率是**每处理器支持的并发用户数**；语言可用线程共享堆、持久对象、惰性加载帮助。

## Key Concepts
- **Expert hacker**：少数、能辨别好坏、决定大多数人用什么语言的人；其意见比"语言设计师"的意见更重要。
- **Trojan horse**：用应用带语言；比直接推广语言有效。
- **Clean and dirty**：好语言的两面性——干净的内核 + 允许 hack 的"流氓"气质。
- **Bottom-up / throwaway origin**：大型系统常由丢弃型程序演化而来。
- **Active profiler**：把性能问题主动推给程序员，而非等提问。
- **Time**：没人想写随时会消失的语言；大多数黑客等语言稳定几年才考虑；"发明者惊讶于需要时间传达信息"。
- **I/O-bound era**：服务器化让很多程序变为 I/O 瓶颈；优化方向从"更快 CPU"转向"更快 I/O 与并发"。

## Mental Models
- 把语言想成**鞋**：再优雅的雕塑，若磨脚就是坏鞋；为脚（黑客）设计。
- 把流行想成**网络效应 + 临界质量**：20 个独立用户是"真的"门槛；之后会自我强化。
- 把设计想成**服务用户而非限制用户**：假设用户是天才，不是白痴；天才需要访问内部。
- 把大型程序想成**从丢弃型演化**：别一开始就设计 Hoover Dam，先从临时建筑开始，让它长成。
- 把性能想成**用 profiler 找瓶颈**，而非用类型系统祈祷；语言要提供"看见"的工具。

## Anti-patterns
- **设计"让 software engineer 摇头"的语言**：让"软件工程师"短语使用者不快的特性，恰恰是 hacker 喜欢的；Pascal 式端庄只适合教学。
- **用英语式长句代替抽象**：`add x to y giving z` 是对黑客智商的侮辱；`z = x + y` 即可。
- **保护用户免受他自己伤害**：你救不了他写错问题的烂程序；阻止他访问内部，只会逼他用更笨的方式。
- **把库当附属品**：库太大会让"找函数"比"写函数"更慢；库也要正交、可预测。
- **只写快编译器**：设计者用"快编译器"衡量自己，但用户需要的是"找到瓶颈"的工具；做错了问题。
- **期待语言一夜流行**：需要时间；发明者常被"没人一开始就用"吓到。

## Worked Example
**Perl 的诞生路径**：Perl 起初不是设计成编程语言，而是一组**系统管理工具**（生成报表的 shell 脚本集合），本质上是丢弃型程序；随着人们用它写的丢弃型程序越来越大，它才（到 Perl 5 前后）成为能写严肃程序的完整语言——但它早在那之前就已大量流行。这是"大型系统起源于丢弃型程序"的教科书案例：想让你的语言被用于大系统，就得先让它擅长写一小时的小脚本。

**临界质量 = 20 人**：作者估计，若一门语言有 20 个"自己决定"用它的用户，就可算"真的"。从零到 20 最难；最好办法是特洛伊木马——给一个人们想要的应用，恰好写在新语言里。

**"C/Lisp/Smalltalk vs Cobol/Ada/Java"的对仗**：C、Lisp、Smalltalk 是设计者**为自己**设计的；Cobol、Ada、Java 是为**别人**设计的。"若你以为你在为白痴设计东西，那么你即使对白痴也没设计好东西"——因为设计者自己不是用户，且居高临下会腐化设计。

## Key Takeaways
1. 语言好坏的判据是**黑客是否喜欢**，不是论文是否优雅。
2. 流行需要三件套：免费实现 + 薄而好的书 + 一个值得 hack 的系统（最好作为某系统的脚本语言）。
3. 黑客最重 **hackability**：假设用户是天才，给他内部访问权；好语言"干净又肮脏"。
4. 简洁来自**更高抽象**与**短 token**；别用英语式样板哄用户。
5. 想用于大系统，先让语言擅长**丢弃型小脚本**——大系统常由此演化而来。
6. 库将比核心语言更决定未来；库也要正交、可预测，避免"找比写更慢"。
7. 性能靠 **profiler**（甚至主动 profiler），不靠静态类型；服务器时代关键指标是**每处理器并发用户数**。
8. 语言需要**时间**获得信任；别期待即时流行。
