# 第11章：The Hundred-Year Language（百年语言）

## Core Idea
编程语言像物种一样形成演化树，但分支会汇合；**应押注主干**——内核最小、最干净、最能自我表达的语言。语言演化得很慢，因为它更像数学记号而不是硬件技术。随着计算机变得极快，正确的取舍会从"节省机器时间"转向"节省程序员时间"：为写出最省力的 version 1 而设计，把效率交给优化建议与 profiler。百年语言原则上今天就能设计，而且今天就可能好用。

## Frameworks Introduced
- **演化树启发式（Evolutionary tree heuristic）**：Cobol 是死胡同（Neanderthal language）；作者预测 Java 也会是死胡同。留在主干上，是选择"今天好用"语言的实用启发式——即使尼安德特人还有不少，做尼安德特人也很惨。
- **语言 = 公理集 + 其余（Axioms / core）**：任何语言都可分为一组基本算子（公理）与可由其写出的其余部分。长期存活的关键是**公理选得好且少**；"就像买房先看地段，其余以后能修，地段修不了。"
- **好浪费（Good waste）**：硬件变快后，大部分多出来的 cycles 会被浪费；其中一种浪费是好的——**用效率换简洁**。不该在语言语义里塞入纯粹为速度存在的 hack（如 strings 作为独立类型）。
- **语义与实现分离（Separate meaning from implementation）**：只保留 lists，通过给编译器的优化建议让它在必要时把字符串铺成连续字节；而不是在核心语言里同时放 lists 和 strings。
- **Bottom-up programming（自底向上）**：把程序写成一系列层，每一层都是上一层的语言；这产生更小、更灵活、更可复用的程序。**可复用性来自"像语言"，不来自 OO**。
- **以 brevity 为代理（Brevity as proxy）**：最省力的程序接近于最短的程序（按 parse tree 的 distinct syntactic elements 计，不按字符）。语言设计算法：看着一个程序问，"这有没有更短的写法？"
- **向远处瞄准（Aim at the distant point）**：学开车时不要用车头对准近处车道线，而要瞄准远方；设计语言也应有百年目标，即使只关心未来十英尺。

## Key Concepts
- **Evolutionary dead-end**：没有 intellectual descendants 的语言；Cobol 是例子，Java 被预测为下一个。
- **Convergence**：语言分支可以汇合（Fortran 分支与 Algol 后代合并），因为可能性空间较小且突变非随机。
- **Core axioms**：语言的基本算子；越少越好；"cruft breeds cruft"。
- **Programmer time vs machine time**：真正的低效是浪费程序员时间，不是浪费机器时间。
- **Strings / arrays / numbers as derived types**：语义上 strings 是字符 list 的子集，arrays 是整数向量为键的 hash table 子集，numbers 甚至可表示为 n 个元素的 list；它们存在主要是为了效率。
- **Metacircular interpreter**：Arc 最初是跑在 Common Lisp 上的解释器，只有几百行，易读易改；两层解释仍可用。
- **Profiler over compiler**：随着"可接受效率"与"最大效率"的差距拉大，找到瓶颈比让编译器生成快代码更重要。
- **Domain-specific little languages**：会大量繁殖，但应是薄薄一层，让用户看见下面的通用语言。

## Mental Models
- 把语言想成**物种**：不要做尼安德特人；但语言可以杂交，所以要看主干而非单点。
- 把内核想成**房子的地段**：外表、库、工具都能 later fix，核心算子不能。
- 把硬件进步想成**预算增加**：以前买不起的"浪费"现在买得起；好设计会用这笔预算买简洁。
- 把程序想成**文章（essay）**：essay 原义是"尝试"；最好的程序常常是作者一开始并不知道要写什么的探索。
- 把优化想成**先粗后精**：version 1 用 list 做一切，之后再给编译器优化建议；过早优化和过早并行都是错。

## Anti-patterns
- **为机器时间污染语言语义**：为速度加 strings、arrays 等冗余公理，增加学习成本与不一致。
- **过早并行**：并行计算被谈论了几十年，通常仍应在程序生命后期、优化阶段才显式使用；version 1 应忽略它。
- **把 OO 当可复用性的来源**：可复用的是 bottom-up 的"语言层"，不是 OO 本身；OO 给大组织提供了"可持续地写意大利面"的方式。
- **由编译器作者而非应用程序员设计语言**：学术界的"可研究性"约束会选出错误的问题（例如类型系统产出论文，却妨碍真正的 macros）。
- **以当前语言的习惯想象未来**：你对"最省力"的判断已被现用语言塑造；需要刻意突破。

## Worked Example
**去掉 strings**：大多数语言同时有 strings 和 lists；语义上 strings 只是元素为字符的 lists 子集。为什么要有独立类型？只为效率。但"为了效率在语义里加 hack"是 lame 的，也是 premature optimization。正确做法：只保留 lists，另给编译器优化建议，让它在需要时把字符 list 表示为连续字节。Arc 这样做了，作者认为是个 win——有些用正则表达式描述很别扭的操作，用递归函数反而容易。

**更激进的删减**：arrays 是"键为整数向量的 hash tables"的子集；hash tables 是否也能换成 lists？numbers 是否也能表示为 n 个元素的 list？数学上可以，只是"难以忍受地低效"。格雷厄姆不是主张实际计算都用 list，而是主张**核心语言在加入任何实现记号之前**这样定义；实际程序当然可以用二进制表示数字，但那是优化，不是核心语义。这是"当 t 趋于无穷时该押注哪边"的思想实验。

**Arc 的两层解释**：最初的 Arc 是写在 Common Lisp 上的 metacircular interpreter，只有几百行；Common Lisp 实现 CLisp 又跑在字节码解释器上。两层解释，上层"令人震惊地低效"，但语言仍然可用（勉强可用）。这说明：**为了简洁与可理解性，可以承受相当大的运行时浪费**。

## Key Takeaways
1. 选择语言时看**演化树主干**：内核小、干净、能自我表达的语言更可能活得久。
2. 硬件越快，越应**用效率换简洁**；真正的浪费是浪费程序员时间。
3. 语言核心应只含**少量、正交的公理**；其余作为库或优化建议存在。
4. **Bottom-up** 是可复用性的真正来源：把应用的一部分下沉成"写这类应用的语言"。
5. 用**最短程序**作为"最省力"的近似目标；不断问"这能不能写得更短？"
6. 设计语言要**向百年后瞄准**；即使只关心近期，远处目标也会纠正当下的方向。
7. 今天就可能设计出百年语言的核心——有人会说 1958 年就基本设计好了。
