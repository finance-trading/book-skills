# 第15章：Design and Research（设计与研究）

## Core Idea
设计与研究的差别在于 **new vs good**：设计不必新，但必须好；研究不必好，但必须新。二者在顶端汇合——最好的设计用新想法超越前人，最好的研究解决不仅新而且值得解决的问题。把编程语言当作**设计问题**而非研究课题，最大的变化是**以用户为中心**：先问"这是给谁的、他们需要什么"，并且最好让设计者自己就是用户。设计过程本身也重要：尽早做出可运行的原型、持续细化、保持士气——因为"程序的测试不只是成品有多干净，还包括到达成品的路径有多干净"。

## Frameworks Introduced
- **Design vs research**：设计 = 做好东西；研究 = 做新东西。顶端汇合，但日常路径不同：设计从用户出发，研究从"新"出发。
- **用户公理（The user axiom）**：设计始于"这是给谁的、他们需要什么"。注意是 **need**，不是 **want**；不是照单全收客户要求，而像医生：病人说症状，你要诊断真正的问题。
  - 你可以选择任何用户群（新手到专家），但必须选一个；脱离目标用户无法谈好坏。
  - **最好让设计者自己属于目标用户**：为"你认为不如你"的人设计，会腐化设计者；美国住宅项目少有建筑师自己住，就是例子。C、Lisp、Smalltalk 由设计者自用；Cobol、Ada、Java 为别人设计。
- **设计过程即产品（Process matters）**：程序像证明，是棵被修剪过的树，过去到处是错误分支。语言的测试不只是"成品程序看起来多干净"，还包括"到达成品的路有多干净"。只按成品评判，会做出"大理石"式的语言：适合展示完成品，不适合发展想法。
- **Worse is Better / 原型优先**：先快速做出原型给用户，再逐渐细化；不要用"万福玛丽长传"一次性做完整产品——互联网泡沫中无数创业公司这样死掉，作者没听说有成功的。
- **艺术中的原型传统**：金属字体先用毛笔在纸上设计；青铜雕塑先用蜡模；挂毯图案先画在纸上；石头建筑先做小木模型。文艺复兴绘画的"先几笔定大形，再逐步细化"也是同一方法：不要沿轮廓慢慢描，误差会积累，最后线接不上。
- **Oil paint 的启示**：油画之所以激动人心，是因为**成品可以直接从原型长出来**；你可以先画素描，但不被它束缚，可以在完成过程中大改。软件也应如此：原型不必只是模型，可以细化成最终产品。
- **士气（Morale）**：设计的关键变量。画画老师："如果你画的时候觉得无聊，画看起来就会无聊。" 软件规则："**always have working code**"——若一小时后能测试，你就有即时回报。油画家的说法："一幅画永远不会完成，你只是停止工作。"
- **面向用户的语言设计案例**：交互式 toplevel / read-eval-print loop 是巨大优势；若语言要求先声明变量，就无法方便地在 toplevel 里"设 x，然后对 x 做事"；因此**强制类型声明与便利的 toplevel 不相容**——这是从设计过程反推语言特性的例子。

## Key Concepts
- **New vs good**：研究与设计的核心区分；最好二者兼得，但不要混淆日常判据。
- **Need vs want**：用户不知道所有选项，也常误判自己真正想要什么；设计者要诊断。
- **Designer as user**：设计者属于目标用户，是避免居高临下腐化的结构性保障。
- **Marble vs oil paint**：大理石适合完成品，不适合发展想法；语言应像油画，允许改。
- **Prototype refinement**：原型 → 细化 → 成品，同一介质完成；而非"原型/成品"两种材料。
- **Hail Mary strategy**：一次性完整交付；在创业中几乎总是失败。
- **Toplevel / REPL**：交互式开发环境；影响语言设计（动态、少声明）。
- **Morale**：无聊产生无聊的作品；持续可运行的原型维持投入。

## Mental Models
- 把设计想成**医生诊断**：病人说"这里疼"，你要找病因；用户说"我要这个功能"，你要找需求。
- 把语言想成**介质**：大理石适合成品，油画适合探索；编程语言应是油画。
- 把程序想成**修剪过的树**：成品是修剪后的样子，但过程里到处是错误分支；评价介质要看它是否支持修剪。
- 把原型想成**可长大的临时建筑**：二战临时建筑常不拆；丢弃型程序常长成大型系统。
- 把士气想成**燃料**：无聊会渗进作品；保持"这真棒"的感觉，而不是"这帮傻子会喜欢"。

## Anti-patterns
- **Hail Mary 式完整交付**：试图一次长传完成整个产品；互联网泡沫中大量创业公司因此自毁。
- **为你看不起的用户设计**：居高临下会腐化设计；"如果你觉得你在为白痴设计，你大概连白痴用的东西也设计不好"。
- **只按成品评价语言**：同一程序在两种语言里，短的那版很有说服力，但可能掩盖了"设计过程极痛苦"；不要做出"大理石语言"。
- **强制声明/过度约束破坏交互式开发**：若语言必须先在顶部声明所有变量，REPL 的便利就没了；这会反向损害语言设计。
- **把设计当短订单**：用户要什么就给什么；真正的设计要判断需求。
- **忽视士气**：用"这帮傻子会喜欢"的心态做东西，作品会透露出来。

## Worked Example
**简·奥斯汀朗读给家人听**：她的小说之所以好，一个原因是她**大声读给家人听**；因此她从不陷入自我沉溺的"文艺"风景描写或装腔作势的哲学议论（哲学仍在，但织进故事，而不是像标签一样贴上去）。这是"持续校准真实用户"的极端案例：家人就是她的测试用户，朗读就是她的可用性测试。

**文艺复兴素描法**：不要沿物体轮廓慢慢描——误差会累积，最后线接不上；正确方法是先画几条大致对位的快速线，再逐渐细化。这与软件原型一致：先粗后细，允许早期错误，逐步收敛。

**油画的"成品即原型"**：15 世纪油画流行，关键优点是**可以在完成过程中大改**；你可以先画素描，但不被它束缚。软件原型也应能细化成最终产品，而不是"原型用蜡、成品用青铜"的两段式。这样既能利用路上获得的新洞察，也对士气有好处。

**Toplevel 反推语言设计**：Lisp 的 read-eval-print loop 让"设 x，然后对 x 做事"成为自然工作方式；若语言要求先声明变量类型，这种交互就不可能。于是"语言要有便利的 toplevel" + "强制类型声明与 toplevel 不相容" ⇒ "强制类型声明的语言不可能便利"。这是从**设计过程**（而不仅是成品）推导语言特性的范例。

## Key Takeaways
1. 设计问 **"给谁、他们需要什么"**；研究问"这是不是新的、值不值得解"。
2. 最好让**设计者自己就是目标用户**；为"不如你"的人设计会腐化判断。
3. 尽早做**可运行原型**，在同一种介质里细化成成品；避免 Hail Mary。
4. 评价语言/工具要看**到达成品的路径**，不只是成品的外观。
5. **士气是设计变量**；保持"always have working code"，让工作本身有回报。
6. 用户说 want，设计者要诊断 need；但不是照单全收，也不是居高临下。
7. 好的设计过程会反过来揭示正确的技术选择（如 toplevel 与类型声明的冲突）。
